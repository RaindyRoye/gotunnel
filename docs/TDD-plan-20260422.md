# TDD 计划

## 现状

- 仅有 `auth_test.go` 和 `buffer_test.go` 两个测试文件
- 核心网络/多路复用逻辑（hub、link、conn、server、client）零测试覆盖
- `buffer_test.go` 未测试并发场景（`sync.Cond` 的核心用途）
- 代码直接依赖 `net.Conn`、`net.Dial` 等具体实现，mock 困难
- 全局可变状态（`Heartbeat`、`Timeout`、`LogLevel`）影响测试隔离

## 第一阶段：纯函数/工具模块

无需重构，投入产出比最高。

| 模块 | 测试内容 |
|---|---|
| `id_allocator.go` | Acquire/Release 正确性、并发安全、ID 耗尽时阻塞、释放后复用 |
| `mpool.go` | Put/Get 往返、容量检查逻辑、并发安全 |
| `buffer.go` | 补充并发读写场景、Close 后 Pop 行为、容量动态增长 |
| `log.go` | 各级别日志输出格式、LogLevel 过滤逻辑 |

## 第二阶段：引入接口抽象

为核心模块测试铺路。

1. `conn.go` 中的 `Tunnel` 依赖 `io.ReadWriter`，可用 `bytes.Buffer` 做测试
2. `hub.go` 的 `onCtrlFilter` 已是扩展点，可注入测试用控制命令
3. 把 `dial()` / `newListener()` 等函数改为可注入的字段（函数类型），便于测试时替换

## 第三阶段：核心模块单元测试

| 模块 | 测试策略 |
|---|---|
| `conn.go` (Tunnel) | 用 `net.Pipe()` 构造成对的读写端，测试加密/解密往返、分包/粘包 |
| `conn.go` (TunnelConn) | 测试 ChaCha20 加解密一致性、帧格式编解码 |
| `hub.go` | 用 mock `Tunnel` 注入控制命令（LINK_CREATE/LINK_CLOSE 等），验证 link 生命周期管理 |
| `link.go` | 用 `net.Pipe()` 模拟双向数据转发，测试 close 语义（半关闭/全关闭） |

## 第四阶段：集成测试

- 启动 Server + Client（同一进程内），走完完整的 tunnel 建立和认证流程
- 验证端到端数据传输正确性和加密一致性
- 测试重连、心跳超时、多 tunnel 负载均衡等场景

## 工具

```
go test -race -cover ./tunnel/    # 竞态检测 + 覆盖率
go test -fuzz                     # Go 1.18+ 原生模糊测试，适合 auth/conn 的编解码
```

不引入第三方测试框架，标准库 `testing` 足够。

## 实施顺序

从第一阶段开始，先为 `id_allocator` 和 `mpool` 写测试，同时补充 `buffer` 的并发测试。

## Hub 单元测试方案

### 测试挑战

| 依赖 | 问题 | 解法 |
|------|------|------|
| `Hub.tunnel *Tunnel` | 需要真实连接 | `net.Pipe()` + `newTunnel()` |
| `link.conn *net.TCPConn` | 不能用 `net.Pipe` | Hub 的 `onCtrl`/`onData` 只操作 link 的 close 状态和 `wbuf`，**不需要活跃 TCP 连接** |
| `Start()` 阻塞 | 需要 goroutine | `onCtrlFilter` 通道回调做同步 |

### 分层测试

#### Tier 1 — 直接方法调用（无 goroutine，最简单）

直接构造 Hub，调用方法，检查 link 内部状态（同包可访问 `l.rerr`、`l.wbuf`）：

| # | 测试 | 验证 |
|---|------|------|
| 1 | `createLink` / `getLink` / `deleteLink` | link CRUD |
| 2 | `createLink` 重复 ID | 返回 `nil` |
| 3 | `onCtrl(LINK_CLOSE)` | → `aclose`，全关闭 |
| 4 | `onCtrl(LINK_CLOSE_RECV)` | → `rclose`，读侧关闭、写侧存活 |
| 5 | `onCtrl(LINK_CLOSE_SEND)` | → `wclose`，写侧关闭、读侧存活 |
| 6 | `onCtrlFilter` 返回 `true` | 拦截，不执行默认逻辑 |
| 7 | `onCtrlFilter` 返回 `false` | passthrough，执行默认逻辑 |
| 8 | `onCtrl` 不存在的 link | 不 panic |
| 9 | `onCtrl` 未知命令 | 不影响 link |
| 10 | `onData` 路由到 link | `wbuf.Pop()` 得到数据 |
| 11 | `onData` 无 link | `mpool.Put` 回收，不泄漏 |
| 12 | `onData` link 已 `wclose` | `mpool.Put` 回收，不泄漏 |
| 13 | `resetAllLink` | 关闭所有 link |

#### Tier 2 — 通过 pipe tunnel 测试调度（需要 goroutine）

`newPipeTunnels()` 创建 Hub + peer，`Start()` 在 goroutine 中运行，通过 `onCtrlFilter` 的 channel 做同步：

| # | 测试 | 验证 |
|---|------|------|
| 14 | `SendCmd` | peer 收到 control packet，解析出正确的 Cmd |
| 15 | `Send` | peer 收到 data packet，解析出正确的 linkid + payload |
| 16 | `Start` 调度 ctrl packet | `onCtrlFilter` 收到命令 + link 状态变化 |
| 17 | `Start` 调度 data packet | `link.wbuf.Pop()` 得到数据 |
| 18 | `Start` 退出 | tunnel 关闭后 `resetAllLink` |

#### Tier 3 — 集成测试（留给 client/server 测试）

两个 Hub 互连、完整 link 生命周期、心跳等。

### 关键设计点

- `onCtrlFilter` 是天然的测试扩展点 — 用 channel 回调实现同步等待
- Tier 1 中 `createLink` 创建的 link 没有 `conn`，但 `onCtrl` 只调 `aclose/rclose/wclose`（操作 `rerr` 和 `wbuf`），不需要 conn
- `onData` 中 `link.write(data)` 只往 `wbuf.Put`，也不需要 conn
