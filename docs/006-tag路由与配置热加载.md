# Tag 路由与配置热加载

创建日期：2026-09-27

一个 gotunnel server 可以同时接入多个 client，并根据 client 的 tag 将业务连接转发到对应后端。server 支持命令行路由和 YAML 配置；使用 YAML 时，收到 `SIGHUP` 信号后加载新增 tag。

每个 client 进程固定使用一个 tag。多个 client 可以使用相同 tag；需要访问多个 tag 时，启动多个 client 进程。所有 tag 共用同一个 secret，认证成功的 client 可以选择任意已配置 tag。

| Client | Tag | Server 转发目标 |
|---|---|---|
| client A，监听 `127.0.0.1:18080` | `A` | `127.0.0.1:9001` |
| client B，监听 `127.0.0.1:18081` | `B` | `127.0.0.1:9002` |
| 另一台机器上的 client A | `A` | 同一个 `127.0.0.1:9001` |

表中的后端地址由 **server** 访问，因此后端的 `127.0.0.1` 指 server 所在机器。client 的 `-backend` 则填写 gotunnel server 的地址。

## 启动 server

以下命令均从项目根目录执行，先构建程序：

```bash
go build -o bin/gotunnel .
```

路由较少且不需要运行期间新增时，可以直接通过命令行定义：

```bash
./bin/gotunnel -listen=:8001 -secret="your-secret" \
  -route=A=127.0.0.1:9001 \
  -route=B=127.0.0.1:9002
```

每个 `-route` 定义一个 `TAG=host:port` 映射，可以重复使用参数，但不能重复定义同一个 tag。命令行路由使用 server 模式，不能同时指定 `-backend` 或大于零的 `-tunnels`。

需要运行期间加载新 tag 时，创建 `server.yaml`：

```yaml
listen: ":8001"
secret: "your-secret"

routes:
  A: "127.0.0.1:9001"
  B: "127.0.0.1:9002"
```

```bash
./bin/gotunnel -config=server.yaml
```

仓库提供了可参考的 [配置样例](../examples/server.yaml)。实际部署时，server 和 client 的 secret 必须一致。

YAML 配置要求：

- tag 路由模式需要提供 `listen`、`secret`、`routes`；`listen` 和 `secret` 不能为空。
- 允许使用 `routes: {}` 启动空路由表，然后逐步新增 tag。
- `allow_client_backend` 默认 `false`；设为 `true` 时也接受 client 用 `-target` 指定后端，并允许省略 `routes`。详见 [Client 指定后端](007-client指定后端.md)。
- tag 区分大小写，长度为 1–128 个字符，仅允许英文字母、数字、`.`、`_`、`-`。
- 后端必须写成 `host:port`，端口范围为 1–65535；IPv6 示例为 `[::1]:9001`。
- 一份配置只包含一个 YAML 文档；重复 tag、未知配置字段、无效路由会导致校验失败。
- 后端不要求在配置加载时就能连接。域名在建立业务连接时解析，后端不可达只影响对应业务连接。

使用 `-config` 时，不能再指定 `-listen`、`-backend`、`-secret`、`-tunnels`、`-tag`、`-target`、`-route` 或 `-allow-client-backend`，这些冲突会在启动时报告。日志、心跳和超时参数仍可单独设置：

```bash
./bin/gotunnel -config=server.yaml -log=2 -heartbeat=10 -timeout=30
```

首次启动时如果配置无效，server 会退出并报告错误。

不再支持 `reload_interval`。如果已有 YAML 使用了这个字段，请删除；保留它会作为未知字段报错。

## 启动 client

分别启动使用 A、B 的两个 client 进程：

```bash
./bin/gotunnel -listen=127.0.0.1:18080 -backend=server:8001 \
  -tunnels=4 -tag=A -secret="your-secret"

./bin/gotunnel -listen=127.0.0.1:18081 -backend=server:8001 \
  -tunnels=4 -tag=B -secret="your-secret"
```

将 `server:8001` 替换为实际的 gotunnel server 地址。两个命令分别运行在各自的终端或进程管理器中。

业务应用连接 client 的本地监听端口即可，不需要在 TCP 数据中携带 tag：连接 `18080` 的流量到达后端 A，连接 `18081` 的流量到达后端 B。

`-tunnels=4` 表示该 client 维护四条持久隧道，它们都使用同一个 tag。每条隧道可以承载多条业务 TCP 连接。修改进程使用的 tag 需要重新启动该 client。

## 信号触发 reload，只追加新 tag

使用 `-config` 启动后，server 只在收到 `SIGHUP` 时重新读取 YAML。保存文件本身不会触发 reload，平时不轮询文件。

每次 reload 都按启动时的文件路径读取当前内容，因此支持普通保存和编辑器替换文件，也不依赖修改时间、大小或文件身份是否变化。

server 先校验整份配置，再一次性加入所有新增 tag。某个 tag 一旦成功加载，在 server 本次运行期间就固定使用该后端地址。

| YAML 的变化 | 收到 `SIGHUP` 后的行为 |
|---|---|
| 新增 tag C | 加入路由表；使用 C 的 client 可以接入 |
| 修改已有 tag A 的后端 | 忽略修改，继续使用首次加载的映射，日志提示需重启 |
| 删除已有 tag B | 保留 B 及其映射，日志提示需重启 |
| 修改 `listen` 或 `secret` | 保留原值，日志提示需重启；文件中合法的新 tag 仍可加载 |
| 修改 `allow_client_backend` | 保留启动时的值，日志提示需重启；文件中合法的新 tag 仍可加载 |
| 配置无效 | 拒绝整次更新，不加载其中任何新 tag，保留当前路由 |
| 文件暂时消失或不可读 | 保留当前路由并记录错误；文件恢复后需再次发送 `SIGHUP` |

例如，在前面的 YAML 中增加 C：

```yaml
listen: ":8001"
secret: "your-secret"

routes:
  A: "127.0.0.1:9001"
  B: "127.0.0.1:9002"
  C: "127.0.0.1:9003"
```

保存完整配置后，在另一个终端发送信号，将 `12345` 替换为 server 进程的 PID：

```bash
kill -HUP 12345
```

server 处理信号后会记录 `config reload: completed`，无需重启，已有连接继续转发。可以用第三个 client 访问 C：

```bash
./bin/gotunnel -listen=127.0.0.1:18082 -backend=server:8001 \
  -tunnels=4 -tag=C -secret="your-secret"
```

如果 C 的 client 已提前启动，它会先因未知 tag 被拒绝；发送信号并加载 C 后，该 client 按现有重连退避机制再次尝试，成功后即可使用。发送信号不会主动唤醒 client 的重连等待。

`SIGHUP` 仍保留原来的状态和 goroutine 数量输出。未使用 `-config` 的 server 和 client 保持原来的信号行为；`SIGINT`、`SIGTERM` 仍用于退出程序。

修改和删除被忽略的规则，同时适用于已有连接、同一持久隧道上的新业务连接，以及之后重新建立的隧道。重新添加一个曾从 YAML 中删除的 tag，也不会覆盖 server 内存中保留的映射。

如需让修改或删除生效，应重启 server。重启后 server 按 YAML 完整重建配置；重启本身会中断已有连接。

## 与原有行为兼容

原来的单后端启动方式保持不变：

```bash
# Server
./bin/gotunnel -listen=:8001 -backend=127.0.0.1:9001 -secret="your-secret"

# Client
./bin/gotunnel -listen=127.0.0.1:18080 -backend=server:8001 \
  -tunnels=4 -secret="your-secret"
```

不使用新参数时，继续使用原有默认值、认证握手和转发流程。兼容关系如下：

| Server 模式 | 不带 tag/target 的 client | 带 tag 的 client |
|---|---|---|
| 旧版 server | 保持原行为 | 拒绝连接 |
| 新版单后端 server（`-backend`） | 保持原行为 | 拒绝连接 |
| 新版路由 server（`-route` 或 `-config`） | 拒绝连接 | 已配置 tag 可以接入；未知 tag 被拒绝 |

因此，可以先升级一端，在单后端模式下继续与旧版另一端互通。切换到 tag 路由模式时，两端都需要使用支持 tag 的版本。

tag 请求及 server 的确认结果会绑定到本次认证并校验签名。tag 是路由键，所有 tag 仍共享 secret；它不提供按 client 划分的访问权限。

## 排查常见问题

| 现象或日志 | 检查项 |
|---|---|
| `unknown tag` | 检查 tag 大小写、server 中是否已经加载该 tag，以及最近的配置加载日志 |
| `route ... handshake failed` | 检查两端是否均支持 tag，并确认 server 使用路由模式；进一步查看错误中是否包含未知 tag |
| 认证失败 | 检查 client 与 server 的 secret 是否一致；运行期间修改 YAML 中的 secret 不会生效 |
| 保存后新 tag 未生效 | 确认已向使用 `-config` 启动的 server 进程发送 `SIGHUP`，并检查 reload 日志 |
| `config reload` 报错 | 修正整份 YAML 后再次发送 `SIGHUP`；失败期间仍使用已加载的路由 |
| `restart required` | 已有映射、监听地址、secret 或 `allow_client_backend` 被修改，这些更改需要重启 |
| 后端连接失败 | 检查 server 所在机器能否访问目标地址及端口 |

成功新增时会记录 `config reload: added tag`，成功完成时会记录 `config reload: completed`。每次处理 `SIGHUP` 都会重新读取并校验配置；失败不会终止 server，也不会自动重试。
